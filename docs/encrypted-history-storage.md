# Chrysalis 0.9.0 storage implementation and launch decision

The owner chose password-free viewing with temporary activity by default, and optional encrypted persistent history. This supersedes the pending product choice in the historical 0.8.0 decision. The timer, first-visit introduction, pause/resume, breaks and all YouTube visibility controls never require unlocking history.

## Every stored field

Source of truth: `extension/src/shared/types.ts`, `persistence.ts`, `crypto.ts`, `background.ts` and `session/model.ts`. No sync, IndexedDB, cookie or remote persistence is used by the extension.

Chrome memory storage is documented as cleared on browser restart, extension reload/update/disable. A service-worker restart is different and preserves session storage. Minimum Chrome is now 114 for the documented 10 MB session allowance. Both Chrome stores are restricted to trusted extension contexts before use, and messages from content scripts cannot request vault operations or private snapshots.

## Cryptography and failure behavior

The implementation uses browser Web Crypto, PBKDF2-HMAC-SHA256 with 600,000 iterations, a fresh 128-bit random salt per vault, and a 256-bit AES-GCM key. Every write has a fresh random 96-bit IV and a 128-bit authentication tag. The version, algorithm, KDF and salt are authenticated as additional data. Envelope shape/length and decrypted payload schema are validated. The 12–128-character password is neither stored nor logged. Imported AES keys are non-extractable; equivalent derived bytes exist only in trusted **memory-backed** `storage.session`, so worker suspension does not demand another password. This is not a claim that all key material is nonextractable. JavaScript cannot guarantee zeroization; device compromise, swap, crash dumps and backups are outside this design.

Lock removes the memory key, decrypted archive and saved completed records; an ongoing timer remains usable. New sessions while locked stay temporary and merge on unlock (latest 100; the UI warns that the oldest extras are removed). Browser restart clears unfinished/unsaved activity and locks durable history. There is no password recovery or export/import. Forgotten passwords require confirmed deletion to start new encrypted history.

The store serializes vault and session operations. An encrypted-history write failure keeps Finish and the memory record usable, marks unsaved changes prominently, and provides Retry. Lock is refused until retry succeeds or the user deletes history. Closing Chrome then can lose those unsaved changes. Preference/session-store failures are reported rather than reported as saved. Confirmed clear-history/reset-all atomically writes a durable tombstone before memory cleanup so failed cleanup cannot resurrect ciphertext or stale records. Delete-one and reflection updates need a successful encrypted save; the UI reports a pending retry when it fails.

## Explicit 0.8.0 migration

On upgrade at the same installation ID, the one old plaintext root is retained unchanged and a prominent history choice is shown. New activity is session-only. No old activity is automatically loaded into current timing. The user can (1) enter/confirm a password and confirm encryption, or (2) confirm deletion. Cancel does neither. Encrypt merges existing completed records with the new browser records, retaining the latest 100, archives an unfinished old plan without resuming it, and discards old timing anchors, identifiers and command receipts. The confirmation explicitly explains those consequences. Preferences survive either choice.

Encryption round-trips the complete payload before a single local replacement of the old root, then verifies the written value. There is no separate plaintext backup. A failed local write leaves the old record; failure after successful replacement leaves the ciphertext for later unlock. Unsupported old records are preserved, with encryption unavailable and an explicit destructive deletion option. There is no promise to erase Chrome database remnants or device backups. The preserved 0.8.0 ZIP/tag is never rewritten.

## Policy reasoning (official pages reviewed 2026-09-08 UTC)

The [Chrome Web Store User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq) covers locally handled sensitive data and encryption at rest. Local-only operation is not a disclosure exemption. This design removes routine activity persistence and encrypts optional history; access control alone is not presented as encryption. Existing plaintext remains a disclosed, user-controlled migration condition, not an assertion that untouched 0.8.0 is encrypted. The implementation resolves the owner's storage decision, but Google still assesses policy compliance; no approval is guaranteed.

The [privacy dashboard instructions](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy) require purpose, permissions and data-use declarations. Proposed categories are User activity, Website content, Web history (transient address inspection only), and Authentication information (the local history password/key, not account login). Free text may contain information the user supplies; no financial, health, identity, private-communications or precise-location feature is solicited. The publisher must review the actual current dashboard wording and certify it accurately. See `extension/distribution/STORE_DRAFT.md` and the matching `extension/PRIVACY.md`.

[Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage) establishes memory lifetime and access restrictions. [Web Crypto](https://www.w3.org/TR/WebCryptoAPI/) specifies the standard primitives. The PBKDF2 work factor follows [OWASP's PBKDF2-HMAC-SHA256 guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); password quality still matters against offline guessing.

The public website separately saves theme preference; Vercel receives ordinary HTTP requests. Voluntary GitHub issues/email go to those providers, not through extension telemetry. No extension runtime fetch, beacon, socket, analytics or remote code was added. The hosted 0.9 policy must be publicly accessible before Store submission: an authenticated preview alone is insufficient. This task does not change production routing.

See the version-bound release validation and CI for actual pass results; source tests alone are not live YouTube or Store approval evidence.
